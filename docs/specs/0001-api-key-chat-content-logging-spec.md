# 需求规格说明书：记录不同 API Key 问答明细与日志审计查看

## Problem Statement

在当前 New API 体系中，网关充当大模型调用的调度与计费中心，支持多用户与多 API Key（Token）并发分发。然而，在实际管理与安全审计场景中存在如下核心痛点：
1. **内容黑盒无法溯源**：当前日志系统仅记录调用元数据（如耗时、Token 数量、扣减额度），不保存用户的具体提问（Prompt）与模型输出（Completion）。当出现恶意调用、数据泄露违规、越狱攻击或业务客诉时，管理员无法核实当时真实的问答上下文。
2. **缺乏 Key 维度的对话审计**：当企业为不同员工、子业务系统分配不同的 API Key 时，无法按 Key 追踪具体产生了哪些对话内容。
3. **海量长文本直接落库的性能风险**：如果盲目无节制地将数十万 Token 的完整上下文全量写入关系型数据库（PostgreSQL/MySQL），会导致数据库空间爆炸并拖垮高并发结算性能。

## Solution

根据产品访谈确认的决策方案（**ABA：单轮最大长度截断保护 + 全局默认启用 + 细粒度权限隔离查看**）：

1. **后端数据库与上下文支持**：
   - 在主日志表（`Log`）中新增 `prompt_content` 与 `completion_content` 两个长文本字段；
   - 在流经核心管道（`RelayInfo`）时捕获该请求的用户提问与大模型回复。
2. **截断与保护策略（Decision A）**：
   - 提取当前对话的关键问答内容（单次请求的 Prompt 与模型输出），并设置单项 10,000 ~ 20,000 字符上限截断，既保留核心审计信息，又防止数据库写入阻塞。
3. **全局默认启用（Decision B）**：
   - 默认开启对话审计捕获，无需繁琐前置配置，所有走文本转发（Chat Completions 流式 / 非流式）的请求在扣款落库时一并持久化问答内容。
4. **前端日志交互与权限隔离（Decision A）**：
   - 在前端「日志」表格操作列增加「查看对话 / 问答详情」弹窗；
   - 严格遵循权限隔离：普通用户只能查看自身名下 API Key 产生的问答内容，超级管理员可审阅全站所有 Key 的问答内容。

## User Stories

1. 作为企业安全管理员，我想要在后台审计特定 API Key 的问答记录，以便在发生数据安全合规审查时调取真实发生的提问与回复。
2. 作为系统运维人员，我想要所有大模型的流式和非流式对话在扣费落库时自动记录问答内容，而无需在每个渠道逐一手动配置。
3. 作为超级管理员，我想要在日志列表的某一笔消费记录后点击“查看对话”，弹窗直观查看格式化的提问与回答并支持一键复制，以便快速确认调用事实。
4. 作为数据库维护人员，我想要网关在存储超长 Prompt/Completion 时自动执行最大字符截断（如 20,000 字符），以保护 PostgreSQL 不被偶发大文件或极端攻击打爆。
5. 作为控制台普通用户，我想要在登录后查看自己创建的 API Key 产生的问答记录，以便核对扣费细节与调试自身开发的应用。
6. 作为普通用户，我不能在日志页面看到其他用户或管理员名下 API Key 的问答明细，以确保租户之间的隐私绝对隔离。
7. 作为流式调用（Stream SSE）的客户端，我想要正常享受极速打字机输出，同时网关在后台并发无感知地聚合完整回复并安全落库。

## Implementation Decisions

1. **数据模型层 (Schema)**：
   - 扩展核心日志结构体（`model.Log`）：新增 `PromptContent` (`gorm:"type:text"`) 与 `CompletionContent` (`gorm:"type:text"`) 字段；
   - 扩展日志创建参数结构体（`model.RecordConsumeLogParams`）以接收这两个字段。
   - 兼容现有数据库自动迁移（GORM `AutoMigrate` 自动为 PostgreSQL 添加列）。
2. **请求上下文契约 (Relay Contract)**：
   - 在全局请求上下文（`relaycommon.RelayInfo`）中挂载 `CapturedPrompt` 与 `CapturedCompletion` 临时属性；
   - 输入阶段（`TextHelper`）：从已解析的请求消息体提取最新提问内容，执行安全长度截断后存入上下文；
   - 输出阶段：
     - 非流式（`OpenaiHandler`）：提取 `Choices` 中的模型响应文本并暂存；
     - 流式（`OaiStreamHandler`）：复用现有的流式内容收集器（`responseTextBuilder`），在流结束、触发计费落库前挂载至上下文。
3. **结算落库阶段 (Settlement)**：
   - 在文本消费结算（`PostTextConsumeQuota`）中，组装参数并将问答内容透传至 `RecordConsumeLog` 写入数据库。
4. **API 与权限契约 (API & Authz)**：
   - 日志查询接口（`GET /api/log` 与 `GET /api/log/self`）自动输出新增的问答内容；
   - 原生接口已有查询范围隔离：非管理员用户查询强制限制在 `user_id = current_user`，天然实现权限隔离。
5. **前端交互层 (Web UI)**：
   - 在前端日志详情弹窗（`DetailsDialog`）或独立的对话抽屉中，渲染「用户提问」与「模型回复」卡片；
   - 接入代码块高亮与 Markdown 文本渲染，配备一键复制按钮与滚动区域。

## Testing Decisions

1. **高质量端到端行为测试准则**：
   - 不测试内部字符串构建器的拼装细节，只测试外在契约：当携带特定 API Key 发送请求后，对应产生的 `LogTypeConsume` 日志记录必须包含非空的 `PromptContent` 与 `CompletionContent`。
2. **测试模块覆盖**：
   - 非流式与流式 Chat Completions 转发集成测试；
   - 字符超长截断边界测试（验证超长输入不会导致数据库插入报错，且长度符合安全上限）；
   - 权限隔离接口测试（验证普通用户通过 API 无法检索出其他用户的问答内容）。

## Out of Scope

1. 本需求不涉及多模态大文件（如上传的几百兆视频、高清音频原文件）的物理二进制文件留存，多模态仅保留文本描述或图片链接。
2. 不涉及客户端向 New API 新增独立聊天前端（仍由现有外部客户端如 Cherry Studio / NextChat / TPCowork 直连调用）。
3. 不对历史存量日志进行追溯补充（仅对新产生的调用生效）。

## Further Notes

- 数据库升级向后完全兼容，新列允许为 NULL / 空字符串。
- 如后续有精细化审计需求，可在系统设置面板预留“问答记录长度限制”配置项。
